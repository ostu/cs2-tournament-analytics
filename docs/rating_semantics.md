## 1. Ключевой принцип: коды `Na/Nc/Nn/Nt` — это стадии ОДНОГО цикла, не разные турниры

`8a`, `8c`, `8n`, `8t` — это четыре стадии рейтингового цикла турнира №8, а не четыре разных
турнира. Модель данных должна разделять:

| Поле | Смысл | Пример |
|---|---|---|
| `tournament_number` | номер турнирного цикла | `8` |
| `rating_stage` | буква стадии (`a`/`c`/`n`/`t`) | `a` |
| `rating_stage_order` | порядок стадии внутри цикла | `10` |
| `rating_code` | исходный код как в источниках | `8a` |
| `dashboard_filter_code` | то, что видит пользователь в фильтре дашборда | TBD (см. `dashboard_spec.md`) |

**Предложенная кодировка** (`a→10, c→20, n→30, t→40`) **не противоречит фактическим данным**:
- стадия `a` (`elo_norm.xlsx`, суффикс `a`) логически предшествует калибровке;
- стадия `c` (`elo_changes.xlsx`, суффикс `c`) — калибровочные карты, играются после входа `a`;
- стадия `n` (`elo_norm.xlsx`, суффикс `n`, встречается только как `7n`) — блендинг после `c`,
  до начала турнира;
- стадия `t` (`elo_changes.xlsx` + `tournament_results.xlsx`, суффикс `t`) — сам турнир,
  играется последним.

Прямых числовых доказательств порядка `a<c<n<t` в самих файлах нет (нет временных меток
уровня стадии), но порядок согласуется с описанием пользователя и с тем, что `n`-стадия
существует только для последнего цикла (7) — логично для стадии, которая используется для
формирования команд **перед** играемым турниром, а не ретроспективно.

### Формат `tN` — только историческое обозначение

`cs_farpost_tournament_score.xlsx` использует `t1`..`t7` (буква-номер), а M-запрос
`tournaments` (в `powerquery.txt`) строит `Tournament` в том же формате `t1`..`t7`, потому что
он извлекается из имён колонок `players.xlsx` (`t1_team`, `t1_elo_start`, ...) — то есть формат
`tN` пришёл из структуры широкой таблицы `players.xlsx`, а не является самостоятельным кодом
стадии. Он **не различает** стадии `a/c/n/t` — `players.xlsx` хранит только "elo_start",
"elo_calib", "elo" (финал) на цикл, без отдельной колонки для `n`-стадии. Именно поэтому
`_startElo` (DAX) и `tournaments`-таблица **не могут** использовать `tN` как основной ключ
рейтинговой стадии — в новой модели `tN` сохраняется только как `dashboard_filter_code`
(отображаемое значение для обратной совместимости с привычными фильтрами), но не как первичный
идентификатор.

## 2. `Na` — normalized entry rating (пример `8a`)

### Authoritative-формула (от пользователя)

```
new_rating_i = previous_final_rating_i * target_returning_total / actual_returning_total
target_returning_total = returning_player_count * 1000
actual_returning_total = sum(previous_final_rating игроков, которые возвращаются)
Новым игрокам: rating = 1000.
```

### Что реально в notebook

Функция `build_elo_diff_table` (`cs_farpost_tournament.ipynb`, ячейка 5) **не содержит** этой
формулы. Она вычисляет только **разницу** (`elo_diff`) между уже существующим значением
`t{n}_elo_start` (взятым из `players.xlsx` как данное) и `elo`, с которым игрок закончил свой
предыдущий турнир:

```python
if pd.isna(last_elo):
    elo_diff = start_elo             # первый турнир игрока — вся стартовая величина
else:
    elo_diff = start_elo - last_elo  # разница относительно предыдущего результата
```

Это значит: **сама пропорциональная нормализация (rescaling) не реализована ни в одной из
двух тетрадей** — они лишь ОТЧИТЫВАЮТСЯ о разнице, предполагая, что `t{n}_elo_start` в
`players.xlsx` уже посчитан правильно каким-то другим (не входящим в переданные файлы)
процессом или вручную.

### Проверка формулы на реальных данных (`players.xlsx`)

Проверено для турниров 2..7 (турнир 1 — начальный, без вернувшихся игроков):

| Турнир | Вернулось | Новых | Σelo_start вернувшихся (факт) | Целевая сумма (`N×1000`) | Совпадает? |
|---|---|---|---|---|---|
| 2 | 35 | 12 | 35000.0 | 35000 | ✅ точно |
| 3 | 18 | 2 | 18000.0 | 18000 | ✅ точно |
| 4 | 18 | 9 | 18000.0 | 18000 | ✅ точно |
| 5 | 18 | 7 | 18500.0* | 18000 | ⚠ см. ниже |
| 6 | 29 | 11 | 29000.0 | 29000 | ✅ точно |
| 7 | 28 | 8 | 28000.0 | 28000 | ✅ точно |

`*` На турнире 5 один новый игрок (обозначен здесь как `Player-Delta`, идентификатор
анонимизирован) получил `elo_start = 500`, а не `1000` — это
единственное найденное отклонение от правила "новый игрок = 1000". Причина неизвестна и не
восстанавливается по имеющимся файлам (см. `docs/unresolved_questions.md`).

**Групповое ограничение (Σ=N×1000) подтверждено ТОЧНО во всех проверенных турнирах.**
Индивидуальная пропорциональная формула (`new_rating_i = prev*factor`) при этом подтверждается
с разной точностью по турнирам:

| Турнир | Средняя |ошибка| формулы на игрока | Точных совпадений |
|---|---|---|
| 2 | 100.1 | 0 из 35 |
| 3 | 28.0 | 0 из 18 |
| 4 | 2.4 | 1 из 18 |
| 5 | 32.8 | 0 из 18 |
| 6 | 12.2 | 9 из 29 |
| 7 | 0.3 | 27 из 28 |

Точность формулы **растёт со временем** (турнир 7 — почти идеальное совпадение, турниры 2/3/5
— заметные расхождения при точном совпадении лишь агрегата). Наиболее вероятная интерпретация:
агрегатное ограничение (сумма = N×1000) выполнялось всегда, но точный алгоритм
индивидуального распределения на ранних циклах, возможно, отличался от чистой пропорциональной
формулы (например, ручная корректировка, округление на промежуточном шаге, группировка по
командам) — этого нельзя восстановить без дополнительного источника. **Формула из ТЗ не
отброшена и не заменена** — она подтверждена на агрегатном уровне и близко совпадает
индивидуально для последних циклов; расхождение зафиксировано как открытый вопрос, не как
"опровержение".

### Обработка игроков без предыдущего рейтинга и пропуска турниров

`build_elo_diff_table` использует переменную `last_elo`, которая **обновляется только когда
`t{t}_elo` не NaN**, и **не сбрасывается**, если игрок пропустил турнир — то есть при пропуске
одного или нескольких циклов "предыдущий финальный рейтинг" берётся из **последнего турнира, в
котором у игрока ЕСТЬ данные**, а не обязательно из непосредственно предшествующего цикла. Это
единственная явно закодированная деталь про "пропуск турниров", которая точно
подтверждена. Как эта деталь сочетается с authoritative-формулой пользователя (которая говорит
только про "предыдущий финальный рейтинг" без уточнения про пропуски) — не противоречит ей,
скорее уточняет "предыдущий" как "последний, в котором участвовал".

### Округление и коррекция остатка

**Не найдено.** Ни в одной из тетрадей нет кода, который явно округляет `Na` до целого с
последующей коррекцией остатка (обычная техника "largest remainder" для точного попадания в
целевую сумму при целочисленном округлении). В `players.xlsx` значения `t{n}_elo_start` — целые
числа, значит округление где-то происходит, но алгоритм остатка не воспроизводится по
имеющимся файлам.

## 3. `Nc` — calibration rating (пример `8c`)

### Notebook: `cs_farpost_tournament_calib.ipynb`

Полностью восстановленная последовательность (ячейка 3):

1. Старт: `elo = t{n}_elo_start` (то есть `elo` инициализируется значением `Na`).
2. Автоматическое распределение по командам **на калибровке НЕ реализовано в этом коде** —
   команды на калибровку формируются отдельным блоком (ячейки 6-9, см. ниже), который в этой
   тетради идёт **после**, а не до основного расчёта `elo`, и работает с данными ОДНОГО
   конкретного калибровочного матча (`players.map{N}==1`), а не всего блока калибровки.
3. Для `koef` в `[0.2, 0.15, 0.1]` (в этом порядке) и для каждой карты калибровки:
   - `combo = 3·Σkills + Σassists + 5·Σmvps + 0.2·Σadr` (сумма по игрокам этой карты);
   - `elo_map[игрок] = round((3·kills + assists + 5·mvps + 0.2·adr)/combo · Σelo)`;
   - `elo_diff_map_koef = round((elo_map - elo)·koef)`;
   - `elo += elo_diff_map_koef` (накопление внутри прохода и между проходами).
4. Итоговый `elo` после всех карт и всех 3 проходов = **`Nc`** (в `players.xlsx` — `t{n}_elo_calib`).
5. По картам сохраняется агрегированный по всем 3 проходам `elo_diff` → это калибровочные
   строки `cs_farpost_elo_changes.xlsx` (код `Nc`, например `8c`).

### Автоматическое распределение по командам на калибровке

Формула автобалансировки команд, описанная пользователем ("на калибровке игроки автоматически
распределяются так, чтобы суммы были максимально близки"), **найдена**, но в ОТДЕЛЬНОМ блоке
кода (ячейки 6-9 `cs_farpost_tournament_calib.ipynb`), не в основном расчётном блоке (ячейка 3):

```python
def divide(my_list):
    lower_difference = sum(elo) + 1
    for partition in combinations(my_list, 5):     # полный перебор всех сочетаний по 5
        remainder = complement(partition, my_list)
        diff = difference(partition, remainder)     # |Σelo(A) - Σelo(B)|
        if diff < lower_difference:
            lower_difference = diff
            solution = [partition, remainder]
    return solution
```

Это полный перебор (`itertools.combinations`) всех сочетаний 5 из 10 игроков одного
конкретного калибровочного матча, минимизирующий разницу суммарного `elo` между двумя
командами. Работает **на уровне одного матча (10 игроков → 2 команды по 5)**, не на уровне
всего калибровочного блока турнира — то есть это подтверждает механизм "как формируются
команды НА ОДНУ калибровочную игру", но не описывает, как из серии калибровочных игр
получается финальный `Nc`.

## 4. `Nn` — post-calibration normalized/blended rating (пример `8n`)

### Authoritative-описание (от пользователя)

Смешивание `Nc` (свежая калибровка) + финал последнего турнира (если игрок в нём участвовал) +
финал предпоследнего турнира (если участвовал), с большим весом свежему турниру, затем
нормализация `Σ(Nn) = player_count × 1000`. Используется для формирования постоянных команд;
целевая сила команды `5000 ± 200`.

### Notebook: `calculate_elo_final` (`cs_farpost_tournament_calib.ipynb`, ячейка 3)

```python
def calculate_elo_final(row):
    t5_valid = notna(row["t5_elo"]) and row["t5_elo"] != 0
    t6_valid = notna(row["t6_elo"]) and row["t6_elo"] != 0
    if t5_valid and t6_valid:
        return 0.3 * row["t5_elo"] + 0.5 * row["t6_elo"] + 0.2 * row["elo"]
    elif t6_valid and not t5_valid:
        return 0.7 * row["t6_elo"] + 0.3 * row["elo"]
    elif t5_valid and not t6_valid:
        return 0.6 * row["t5_elo"] + 0.4 * row["elo"]
    else:
        return row["elo"]

elo_final = elo_final * (1000 * len(elo_m2)) / elo_final.sum()
elo_final = round(elo_final).astype(int)
```

где `row["elo"]` на этом шаге — это уже посчитанный `Nc` (`t7_elo_calib` для цикла 7), `t5_elo`
и `t6_elo` — финалы турниров 5 и 6 (для цикла N — это "предпоследний" и "последний" турниры
относительно N=7 в примере кода).

**Это ТОЧНО совпадает с authoritative-описанием пользователя**, включая:
- три источника (калибровка + 2 последних турнира);
- больший вес более свежему турниру (`0.5` для `t6` > `0.3` для `t5`);
- запасные варианты, если один из турниров пропущен (`0.7/0.3` или `0.6/0.4`);
- финальная нормализация на `player_count × 1000` (**подтверждено на реальных данных: сумма
  после нормировки = 36000 при 36 игроках с `t7_elo_calib`, см.
  `artifacts/audit_v2/rating_stage_sums.json`**).

**Формула и веса НЕ придуманы — это буквальный код**, единственная "жёсткая" деталь во всех
трёх ветвях — веса `0.3/0.5/0.2`, `0.7/0.3`, `0.6/0.4`, взятые прямо из notebook.

### Несовпадение: происхождение сохранённого `elo_diff` для стадии `n`

`cs_farpost_elo_norm.xlsx` содержит 36 строк с кодом `7n` (тот же набор `id`, что и `7a`), но
эти значения `elo_diff` **не воспроизводятся точно** ни как `Nn(нормированный) − Nc`, ни как
`Nn(до нормировки) − Nc` — направление и порядок величины совпадают (тот же знак, сопоставимый
масштаб), но точного числового совпадения нет (средняя абсолютная ошибка ~85 очков на
проверенных гипотезах). Формула самого блендинга (веса, нормировка) **подтверждена**; то,
относительно какой базы считается сохранённый `elo_diff` для `7n`, **не подтверждено** — не
угадываем эту деталь, фиксируем как открытый вопрос (`docs/unresolved_questions.md`).

Также: экспорт строк `Nn` (`.to_csv` с кодом `n`) **не виден** ни в одной ячейке из
предоставленных версий notebook-файлов — код для получения `elo_final` есть, явного шага
"сохранить как `{n}n`" нет. Скорее всего, соответствующая ячейка была добавлена/изменена в
более позднем прогоне тетради, который до нас не дошёл.

### Целевая сила команды 5000±200

Не проверялась количественно в этом отчёте (нет самого распределения по постоянным командам
для тестирования) — команды на основе `Nn` в имеющихся 5 таблицах не сформированы явно; это
предполагаемое использование, описанное пользователем, но не наблюдаемое напрямую в данных.

## 5. `Nt` — final tournament rating (пример `8t`)

Формула **полностью подтверждена и сверена в трёх независимых источниках**:

1. **Notebook** (`cs_farpost_tournament.ipynb`, ячейка 3): `elo` инициализируется `t{n}_elo_calib`
   (`Nc`), затем то же правило 3 проходов (`koef` 0.2/0.15/0.1) по картам основного турнира.
2. **DAX** (`dax.txt`): `_EloFinal = SUM(tournaments[elo_calib]) + SUM(cs[elo_diff])`.
3. **Реальные данные** (`players.xlsx`): `t{n}_elo` (столбец `Nt`).

Проверка (`artifacts/audit_v2/elofinal_legacy_vs_raw.json`): при суммировании `elo_diff` ТОЛЬКО
по картам основного турнира (`rating_stage == "t"`, без калибровочных карт) DAX-формула
**точно совпадает** с `players.t{n}_elo` для всех 7 турниров, 0 расхождений на 229 проверенных
парах "игрок×турнир". Если не отделять стадию `t` от `c` при суммировании, расхождение
достигает нескольких сотен очков на игрока — прямое доказательство, почему
`tournament_number`/`rating_stage` должны быть раздельными полями.

**Вывод:** `EloFinal` (в терминах Power BI) = `Nt` = `players.t{n}_elo` = `elo_calib +
Σelo_diff(rating_stage='t')`. Это НЕ третья, отдельная величина и НЕ notebook-переменная
`elo_final` (та относится к `Nn`, см. раздел 4) — обе гипотезы Audit v1 о `EloFinal` уточнены
и заменены этим подтверждённым выводом.
