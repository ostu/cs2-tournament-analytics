## 1. Рейтинговый цикл

### 1.1 База для `elo_diff` в стадии `Nn` (код `"7n"`)

**Известно:** формула блендинга (`calculate_elo_final`, веса 0.3/0.5/0.2 и запасные варианты)
и нормализация `Σ=n×1000` точно подтверждены в notebook и на данных (см.
`docs/rating_semantics.md`, §4). **Не известно:** относительно какой величины считается
сохранённый `elo_diff` для `"7n"` — ни `Nn(норм.) − Nc`, ни `Nn(до норм.) − Nc` не совпадают
точно (среднее отклонение ~85 очков, тот же знак и порядок величины, но не точное число).

**Вопрос пользователю:** относительно какой базовой величины считается `elo_diff` для стадии
`n`? Есть ли доступ к ячейке/версии notebook, где явно виден экспорт `{n}n`-строк (в
предоставленных версиях `cs_farpost_tournament_calib.ipynb` такого `.to_csv()`-вызова с кодом
`n` не видно — вероятно, был добавлен в отдельном, не сохранённом прогоне)?

**Что можно сделать без ответа:** зафиксировать `Nn` в модели как отдельное измеримое событие
рейтинга с полем `rating_after` (сама величина `Nn`, подтверждена точно) и оставить
`rating_change`/`normalization_factor` пустыми/не рассчитанными для этой стадии до уточнения.

### 1.2 Индивидуальная формула `Na` на турнирах 2-5

**Известно:** агрегатное ограничение (`Σ elo_start вернувшихся == returning_count×1000`)
подтверждено точно на каждом турнире 2-7. Индивидуальная пропорциональная формула
(`new_rating_i = prev_i × factor`) сходится к почти точному совпадению начиная с турниров 6-7
(средняя ошибка 12.2 → 0.3), но заметно расходится на турнирах 2, 3, 5 (средняя ошибка 100.1,
28.0, 32.8 очка на игрока).

**Вопрос пользователю:** менялся ли процесс нормализации `Na` со временем (например, раньше
считался вручную/по-другому, а начиная с определённого турнира — автоматизирован по формуле из
задания)? Если да — с какого турнира формула должна считаться "канонической"?

**Что можно сделать без ответа:** использовать формулу из задания как каноническую для НОВЫХ
расчётов (турнир 8+), не пытаясь задним числом "исправить" `t2_elo_start`..`t5_elo_start` в
`players.xlsx` — они остаются историческими данными как есть.

### 1.3 Исключение `elo_start=500` у игрока `Player-Delta` (анонимизировано, турнир 5)

### 1.4 Целевая сила команды `5000±200` (использование `Nn`)

## 5. Предложение: `fact_player_rating_event`

Каноническая таблица уровня "одно рейтинговое событие". Поля и статус каждого — по факту того,
что подтверждено в этом аудите (Audit v1 + v2), без придумывания несуществующих значений.

| Поле | Источник | Статус |
|---|---|---|
| `private_player_key` | `players.id` / `tournament_results.id` / `elo_changes.id` | подтверждено |
| `tournament_number` | извлекается из `rating_code` (регэксп на цифры) | подтверждено (метод), см. `pipeline/audit_powerbi_logic.py::parse_rating_code` |
| `rating_stage` | буква кода (`a`/`c`/`n`/`t`) | подтверждено для `a/c/t`; `n` — подтверждено как понятие, детали события — частично |
| `rating_stage_order` | `10/20/30/40` (см. `docs/rating_semantics.md`) | предложено, не противоречит данным |
| `rating_code` | исходный код как в источниках (`"8a"` и т.п.) | подтверждено |
| `event_type` | см. перечень ниже | производное |
| `event_sequence` | порядковый номер события в рамках (`private_player_key`,`tournament_number`,`rating_stage`) | производное, вычислимо |
| `match_id` | `tournament_results.matchId` (только для событий грейна "карта") | подтверждено (с оговоркой на сброс по турнирам) |
| `map_id` | `tournament_results.mapId` / `elo_changes.mapId` (+1, выровнено к 1-based) | подтверждено, требует явного шага выравнивания (см. `powerbi_logic_audit.md` §2) |
| `map_sequence` | = `map_id` после выравнивания | производное |
| `rating_before` | для `a`: последний известный `elo` предыдущего турнира; для `c`/`t`: накопленное значение перед картой; для `n`: `Nc` | частично подтверждено (формулы известны, не все базы для `elo_diff` подтверждены — см. §1.1) |
| `rating_change` | `elo_diff` (по карте — `elo_changes`; по входу — `elo_norm`) | подтверждено для `a/c/t`; частично для `n` |
| `rating_after` | `rating_before + rating_change`, либо прямое значение (`t{n}_elo_start/_calib/_elo`) | подтверждено там, где есть прямая колонка |
| `normalization_factor` | для `a`: `target_returning_total/actual_returning_total`; для `n`: `(1000×N)/Σelo_final_raw` | подтверждено как формула; не для каждого события есть точное числовое пересчитанное значение (см. §1.1-1.2) |
| `source_file` | `cs_farpost_elo_changes.xlsx` / `cs_farpost_elo_norm.xlsx` / `cs_farpost_players.xlsx` / `cs_farpost_tournament_results.xlsx` | подтверждено |
| `source_row` | индекс строки в исходном файле (для трассировки) | производное |
| `formula_version` | версия формулы, применённой при построении витрины (например, `"na_v1_authoritative"`, `"nc_v1_notebook"`) | вводится на этапе моделирования, не существует в источниках |

### Разделение событий (`event_type`)

1. **`previous_tournament_final`** — `rating_after` предыдущего турнира, используется как
   входная точка для расчёта `Na` следующего (не отдельная строка данных, а ссылка/lookup).
2. **`normalized_entry`** — стадия `Na`, одно событие на игрока на вход в турнир.
3. **`calibration_game`** — стадия `Nc`, одно событие на (игрока, карту калибровки).
4. **`calibration_final`** — итоговое значение `Nc` после всех калибровочных карт (одно на
   игрока на турнир — это то же самое значение, что и последнее `rating_after` в цепочке
   `calibration_game`, выделено отдельно для удобства запросов "дай мне итог калибровки").
5. **`blended_normalized_rating`** — стадия `Nn`, одно событие на игрока (только для турниров,
   где эта стадия зафиксирована — сейчас это только турнир 7).
6. **`tournament_map_elo_change`** — стадия `Nt`, одно событие на (игрока, карту основного
   турнира).
7. **`tournament_final`** — итоговое значение `Nt` (аналогично `calibration_final` — то же
   значение, что последнее `rating_after` в цепочке `tournament_map_elo_change`, выделено для
   удобства).

**Важно:** таблица описывает СТРУКТУРУ, не создаётся в этом аудите как физический файл —
следующий этап (построение витрин) должен наполнить её только подтверждёнными значениями,
оставляя `rating_change`/`normalization_factor` пустыми там, где формула не полностью
подтверждена (раздел 1.1, 1.2 этого документа), а не подставляя туда предположения.

## 6. Состав постоянных команд с roster_size != 5

**Известно:** `resolve_final_roster()` (см. `pipeline/build_marts.py`) определяет состав
команды на турнире как множество игроков, для которых команда — их СОБСТВЕННАЯ последняя
сыгранная карта стадии `t` в этом турнире. Диагностика (`pipeline/audit_team_rosters.py`,
`artifacts/validation/team_roster_anomalies.{json,md}`) нашла **12** пар команда×турнир, где
получившийся размер состава != 5 (2, 3, 4, 6 или 7 игроков). Классификация по вероятной причине
на момент последнего прогона:

| Причина | Количество |
|---|---|
| `mid_tournament_transfer` (игрок реально перешёл в другую постоянную команду в течение турнира) | 4 |
| `missing_player_map_rows` (внутри диапазона участия игрока пропущена карта, которую команда играла, включая уже известный случай `Player-Gamma`/турнир 5 (анонимизировано, см. §3.2)) | 6 |
| `final_map_roster_artifact` (фактический последний матч команды сыгран впятером, но `resolve_final_roster()` считает "последнюю карту" ПО ИГРОКУ, а не по команде — из-за этого пришедший под конец турнира новый игрок и окончательно выбывший ранее игрок оба попадают в состав одновременно) | 2 |
| `real_four_player_map`, `substitution`, `conflicting_source_roster`, `unknown` | 0 (в последнем прогоне не встретились, категории оставлены в таксономии на случай будущих турниров) |

Ни один из 12 случаев не был исправлен автоматически: `resolve_final_roster()` не менялся,
Nc/Nt не пересчитывались, состав не дополнялся/не урезался. Добавлен только data-quality флаг
`roster_size_not_five` (см. `docs/data_model.md`) и нейтральное предупреждение в профиле
команды на дашборде.

**Рассмотренные варианты исправления** (подробности, преимущества/риски и влияние на
Nc/Nt/roster/матчевую статистику по каждому — в `artifacts/validation/team_roster_anomalies.md`
и в отчёте агента пользователю):

- **A — официальный состав из источника** (`cs_farpost_players.xlsx`, `t{n}_team`): не
  покрывает все случаи (для части команд/турниров это поле пустое — см. `source_roster_players_xlsx: —`
  в отчёте), но там, где заполнено, это единственный вариант, не зависящий от порядка карт.
- **B — modal roster** (пятёрка, чаще всего встречавшаяся вместе на одной карте): устойчив к
  разовым заменам, но не различает "кто ушёл/кто пришёл" — теряет матчевую статистику
  выбывших/пришедших игроков как участников состава.
- **C — final active roster** (состав фактической последней карты КОМАНДЫ, не игрока): ближе
  всего к бытовому пониманию "состав на конец турнира", решает все 2 случая
  `final_map_roster_artifact` и часть `mid_tournament_transfer`, но требует отдельно решить, что
  делать с заменами (кого учитывать в Nc/Nt — стартовый состав или подставу).
- **D — rating-weighted roster** (официальные игроки для Nc/Nt, фактически сыгравшие — для
  матчевой статистики): не даёт "рассинхрона" между рейтингом и статистикой карт, но требует
  вести ДВА разных состава на одну пару команда×турнир и отдельно объяснить пользователю разницу
  в профиле команды.

**Вопрос пользователю:** какой вариант (A/B/C/D) принять как канонический для `roster_size !=
5`, и стоит ли применять один и тот же вариант ко всем 12 случаям или решение зависит от
`probable_cause` конкретной пары (например, C для `final_map_roster_artifact`, но A/D для
`mid_tournament_transfer`)?

**Что можно сделать без ответа:** оставить `resolve_final_roster()` как есть (уже
подтверждённая логика, см. `tests/test_team_classification.py::TestFinalRosterResolution`),
показывать `roster_size_not_five` как warning (не critical) в `validate_pipeline.py`, и
нейтральное предупреждение в профиле команды на дашборде — без блокировки сборки.
