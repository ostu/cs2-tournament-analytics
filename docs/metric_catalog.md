# Каталог метрик — CS2 Tournament Report (Audit v2)

Обновлено по итогам Audit v2 (`powerquery.txt` + `dax.txt` + authoritative-пояснения
пользователя). Формулы **не реализованы в коде** для дашборда — только задокументированы и
сверены на реальных данных через `pipeline/audit_powerbi_logic.py`
(`artifacts/audit_v2/*.json`). Ничего не придумано за отсутствующие формулы.

Для каждой метрики Audit v2 добавляет там, где применимо:
- **Legacy Power BI formula** — точная формула из `dax.txt` (если есть);
- **Proposed canonical formula** — что предлагается для новой витрины;
- **Отличаются ли результаты** — да/нет/не проверялось, с числами из
  `artifacts/audit_v2/`;
- **Причина отличия**;
- **Решение для HTML-версии**.

Легенда столбца "Источник формулы": **notebook** / **исходная таблица** / **DAX** (`dax.txt`) /
**восстановлено из кода** / **предположительно Power BI** / **отсутствует**.

---

## `kills`, `assists`, `deaths`

- **Бизнес-смысл:** сырые счётчики за карту.
- **Уровень агрегации:** игрок × карта (базовый грейн, подтверждён).
- **Исходные поля:** `tournament_results.kills/assists/deaths`.
- **Источник:** исходная таблица.
- **Legacy Power BI formula:** нет отдельной меры — используются как `SUM(cs[kills])` и т.п.
  внутри других мер (`_avgKills`, `_KD`, `_KR`).
- **Proposed canonical formula:** без изменений — сырые значения на грейне (tournament, mapId, id).
- **Отличаются ли результаты:** нет.
- **Статус:** подтверждена.

## `ADR` (Average Damage per Round)

- **Бизнес-смысл:** средний урон за раунд.
- **Уровень агрегации:** карта (источник) → игрок/команда/турнир (агрегат в визуале).
- **Исходные поля:** `tournament_results.adr`.
- **Legacy Power BI formula:** `_avgADR = AVERAGE(cs[adr])`.
- **Proposed canonical formula:** `AVERAGE(adr) WHERE adr_tracked = true` (см.
  `adr_tracked` — концептуальное поле уровня (tournament, mapId), см.
  `artifacts/audit_v2/adr_mvp_coverage.json`).
- **Отличаются ли результаты:** да, существенно. Legacy (включая untracked-нули) = **26.34**
  глобально; availability-aware (только протрекованные карты) = **78.50** — расхождение почти
  в 3 раза.
- **Причина отличия:** ADR не собирался физически в турнирах 1t-5t/2c-5c (100% строк = 0 в этом
  диапазоне, подтверждено пользователем и количественно). Legacy-формула трактует эти нули как
  реальные низкие значения.
- **Решение для HTML-версии:** показывать availability-aware среднее; там, где у игрока НЕТ ни
  одной протрекованной карты (35 из 84 игроков), показывать "нет данных", а не 0.
- **Статус:** подтверждена (правило `adr_tracked`), legacy формула — не переносится как есть.

## `KD` (Kill/Death ratio)

- **Бизнес-смысл:** отношение убийств к смертям.
- **Legacy Power BI formula:** `_KD = DIVIDE(SUM(cs[kills]), SUM(cs[deaths]))` (сумма-к-сумме,
  не среднее отношений на карту).
- **Proposed canonical formula:** без изменений — `Σkills / Σdeaths` на нужном грейне.
- **Отличаются ли результаты:** нет (формула однозначна и не зависит от сброса `mapId`,
  в отличие от `_avgKills`).
- **Известные ограничения:** `DIVIDE` возвращает `BLANK()` при `Σdeaths=0` — в HTML нужно явно
  показывать "—", а не `0` или `∞`.
- **Дубликат:** `_KD2` — побайтово идентичная формула в `dax.txt`. Каноническая метрика — одна;
  `_KD2` фиксируется как legacy-алиас, не отдельная метрика.
- **Статус:** подтверждена (Audit v1 помечал "формула отсутствует" — снято).

## `KR` (Kills per Round)

- **Бизнес-смысл:** среднее убийств за раунд.
- **Legacy Power BI formula:** `_KR = DIVIDE(SUM(cs[kills]), SUM(cs[rounds]))`.
- **Proposed canonical formula:** без изменений — `Σkills / Σrounds`.
- **Отличаются ли результаты:** нет.
- **Дубликат:** `_KR2` — идентична, тот же статус, что у `_KD2`.
- **Статус:** подтверждена (Audit v1: "формула отсутствует" — снято).

## `avgKills` / `avgKills2`

- **Бизнес-смысл:** среднее убийств за карту.
- **Legacy Power BI formula:** `_avgKills = _avgKills2 = DIVIDE(SUM(cs[kills]),
  DISTINCTCOUNT(cs[mapId]))` — **подтверждённый полный дубль** (побайтово идентичные формулы в
  `dax.txt`; отсюда и разрешение загадки Audit v1 про суффикс "2" — он не имеет смысла).
- **Proposed canonical formula:** `SUM(kills) / COUNT(DISTINCT (tournament, mapId))` — то есть
  тот же принцип, но по составному, а не по одиночному ключу.
- **Отличаются ли результаты:** ДА, значительно.
  - Глобально (все турниры): legacy знаменатель = **32** (уникальные значения `mapId`,
    1..32), canonical = **224** (реальное число уникальных сыгранных карт). Legacy avgKills =
    **1147.8**, canonical = **163.98** — legacy завышает в ~7 раз.
  - На уровне игрока: у **64 из 84** игроков (76%) canonical-знаменатель больше legacy — самые
    задетые (например, `Player-Alpha`: legacy 69.7 vs canonical 23.5, `Player-Beta`: 62.3 vs 22.0;
    игровые идентификаторы анонимизированы в этом документе).
- **Причина отличия:** `mapId` сбрасывается на каждом турнире (не глобальный ключ) —
  `DISTINCTCOUNT(mapId)` в контексте, охватывающем больше одного турнира, считает уникальные
  ЗНАЧЕНИЯ, а не уникальные КАРТЫ.
- **Решение для HTML-версии:** использовать canonical-формулу (составной ключ). Не переносить
  legacy-знаменатель ни в каком виде — расхождение слишком велико, чтобы оставлять как есть
  "для совместимости".
- **Статус:** подтверждена формула Power BI; расхождение с корректным расчётом
  количественно подтверждено (`artifacts/audit_v2/avgkills_legacy_vs_canonical.json`).

## `elo_start` (`Na`)

- **Бизнес-смысл:** нормализованный рейтинг на входе в турнир.
- **Исходные поля:** `players.t{n}_elo_start`.
- **Legacy Power BI formula:** нет отдельной DAX-меры — используется как есть через `tournams[elo_start]`
  (единственный потребитель — `_startElo`).
- **Proposed canonical formula:** см. `docs/rating_semantics.md`, §2 (authoritative-формула
  пользователя). Групповое ограничение подтверждено точно; индивидуальная формула — точно с
  турниров 6-7, с отклонениями на 2-5 (см. `docs/unresolved_questions.md`, §1.2).
- **Отличаются ли результаты:** для турниров 2-5 — да (среднее отклонение 28-100 очков на
  игрока от чистой пропорциональной формулы, при точном совпадении агрегата).
- **Решение для HTML-версии:** показывать исторические `t{n}_elo_start` как есть (это
  зафиксированные исторические данные); для будущих турниров (8+) считать по
  authoritative-формуле.
- **Статус:** подтверждена (историческое значение); формула — частично подтверждена.

## `elo_calib` (`Nc`)

- **Бизнес-смысл:** рейтинг после калибровки, перед турниром.
- **Исходные поля:** `players.t{n}_elo_calib`.
- **Legacy Power BI formula:** используется как `SUM(tournaments[elo_calib])` в `_elo_diff%` и
  `_EloFinal` (нет отдельной меры "elo_calib" — это просто колонка).
- **Proposed canonical formula:** без изменений — колонка-факт; расчёт (notebook, 3 прохода
  koef 0.2/0.15/0.1 от `elo_start`) полностью описан в `docs/rating_semantics.md`, §3.
- **Отличаются ли результаты:** не проверялось (нет достаточных исходных карточных данных
  калибровки за прошлые турниры, кроме текущей).
- **Статус:** подтверждена (как значение и как формула DAX-потребления); частично подтверждена
  воспроизводимость расчёта из карточных данных (см. Audit v1).

## `EloFinal` (`Nt`)

- **Бизнес-смысл:** итоговый рейтинг игрока после основного турнира.
- **Legacy Power BI formula:** `_EloFinal = SUM(tournaments[elo_calib]) + SUM(cs[elo_diff])`.
- **Proposed canonical formula:** то же самое, но с ЯВНЫМ фильтром `rating_stage == 't'` при
  суммировании `elo_diff` (без этого DAX-формула на практике вычисляется в контексте, где
  `cs` уже отфильтрован по одному турниру/стадии визуалом — сама мера этот фильтр не
  гарантирует).
- **Отличаются ли результаты:** НЕТ, если фильтр по стадии соблюдён — точное совпадение с
  `players.t{n}_elo` для всех 7 турниров (0 из 229 проверенных пар "игрок×турнир" разошлись).
  ДА, если фильтр не применён — расхождение до **780** очков на игрока (см.
  `artifacts/audit_v2/elofinal_legacy_vs_raw.json`).
- **Причина отличия (когда возникает):** без разделения `tournament_number`/`rating_stage`,
  суммирование `elo_diff` затрагивает и калибровочные карты (`Nc`), которые уже учтены в базе
  `elo_calib` — получается двойной счёт.
- **Решение для HTML-версии:** реализовать с явным полем `rating_stage` в модели (см.
  `fact_player_rating_event`), не полагаясь на то, что фильтр визуала "магически" ограничит
  контекст правильно.
- **Статус:** подтверждена (Audit v1 помечал "формула отсутствует" со сдвоенной
  неоднозначностью — обе гипотезы Audit v1 заменены этим подтверждённым выводом).

## `elo_diff`

- **Бизнес-смысл:** изменение Elo. Два разных смысла в источниках:
  1. по карте (`elo_changes.elo_diff`, стадии `c`/`t`);
  2. по входу в турнир (`elo_norm.elo_diff`, стадии `a`/`n`).
- **Legacy Power BI formula:** `_elo_diff = SUM(cs[elo_diff])` — учитывает только смысл (1),
  после `LEFT JOIN` со сдвигом `mapId+1` (см. `docs/powerbi_logic_audit.md`, §2).
- **Proposed canonical formula:** то же (`Σelo_diff` на нужном грейне), плюс явный
  `rating_stage` для различения смыслов (1)/(2) вместо смешивания через одноимённую колонку.
- **Отличаются ли результаты:** нет для смысла (1) на уровне карты (1 несовпавшая строка на
  2235 — `5t/mapId10/Player-Gamma` (идентификатор анонимизирован), см. `docs/unresolved_questions.md` §3.2).
- **Статус:** подтверждена (по карте); частично подтверждена (по входу в турнир, стадия `n` —
  см. `docs/rating_semantics.md` §4).

## `elo_diff%`

- **Бизнес-смысл:** относительное изменение Elo.
- **Legacy Power BI formula:** `_elo_diff% = DIVIDE([_elo_diff], SUM(tournaments[elo_calib]))`
  — база подтверждена: **`elo_calib`** (`Nc`), не `elo_start` и не `EloFinal`.
- **Proposed canonical formula:** без изменений.
- **Отличаются ли результаты:** не проверялось количественно (формула теперь однозначна,
  числовая сверка не требуется отдельно от `_elo_diff`/`elo_calib`, которые уже сверены выше).
- **Статус:** подтверждена (Audit v1: "формула отсутствует" — снято).

## Рейтинг игрока / Рейтинг команды

- **Бизнес-смысл:** ранжирование в топ-листах.
- **Legacy Power BI formula:** **не найдена** ни в `dax.txt`, ни в `powerquery.txt` — среди 17
  мер нет `RANKX`-подобной меры для игрока или команды.
- **Proposed canonical formula:** нет.
- **Отличаются ли результаты:** н/п.
- **Решение для HTML-версии:** сортировка таблицы по подтверждённому полю (`EloFinal`/`elo_calib`)
  как временная замена явного рейтинга; не изобретать формулу ранжирования.
- **Статус:** формула отсутствует (не изменилось после Audit v2 — `dax.txt` не содержит такой
  меры).

## Вклад карты в изменение Elo

- **Бизнес-смысл:** карта → изменение Elo игрока/команды.
- **Legacy Power BI formula:** для игрока — то же, что `elo_diff` по карте (`_elo_diff` в
  соответствующем фильтре). Для команды — предположительно через `cs2_team_score`/`_TeamsPP`,
  но эти меры считают `PP` (раундовый дифференциал), не `elo_diff` — то есть **нет DAX-меры,
  которая явно агрегирует `elo_diff` до команды**.
- **Proposed canonical formula:** для команды — сумма или среднее `elo_diff` игроков состава на
  карте (аналогично проблеме `_TeamsPP`, но для elo_diff нет даже денормализованной DAX-меры,
  которую можно было бы сверить).
- **Статус:** подтверждена (игрок); формула отсутствует (агрегация до команды).

## Количество турниров / Количество сыгранных карт

Без изменений относительно Audit v1 — `dax.txt` не содержит отдельных мер для этих
показателей (они, вероятно, реализовывались прямо в визуале через `COUNT`/`DISTINCTCOUNT` без
именованной меры). Статус: количество турниров — частично подтверждена (неоднозначность
"турнир vs турнир+калибровка" не снята); количество сыгранных карт — подтверждена.

## Место команды на турнире

Без изменений относительно Audit v1 по формуле (прямая колонка `tournament_score.place`).
**Новое:** `powerquery.txt` подтверждает, что связь "команда игрока → место на турнире"
реализована через составной текстовый ключ `tournament-team` (турнир+имя команды,
одинаково строится в `tournaments` и в `cs_farpost_tournament_score`) — и что Power Query
**не выполняет** алиасинг названий команд перед этим джойном, то есть расхождения в написании
(раздел про team aliases) реально мешают связке в текущем Power BI отчёте, не только
гипотетически. Статус не меняется: частично подтверждена (зависит от alias-мэппинга,
`config/team_aliases_review.csv`).

## Новые метрики, найденные в `dax.txt` (не было в Audit v1)

### `PP` (раундовый дифференциал матча/карты)

- **Бизнес-смысл:** разница раундов победитель/проигравший, знак — с точки зрения строки.
- **Legacy Power BI formula (в `cs`):** `PP = if [w/l]="W" then [r1]-[r2] else [r2]-[r1]`, где
  `r1/r2` — счёт из `result`, распарсенный через `Table.SplitColumn` по `"-"`.
- **Proposed canonical formula:** то же самое, но на грейне (tournament, mapId, team) — не
  денормализованное на игроков.
- **Отличаются ли результаты:** будет отличаться на строках, где `result` был испорчен Excel'ем
  (79.9% строк, см. `docs/powerbi_logic_audit.md` §3) — там `r1/r2` в текущем Power BI, по
  документированной семантике `Table.SplitColumn`, скорее всего, дают ошибку конверсии, а не
  число.
- **Решение для HTML-версии:** считать `PP` только там, где `result` распознан как
  `valid_score` или где применена согласованная эвристика восстановления (см.
  `docs/unresolved_questions.md` §2.2); не переносить необработанный `result`-парсинг как есть.
- **Статус:** подтверждена формула; данные, на которых она считается, требуют предварительной
  очистки `result`.

### `_TeamsPP`

- **Legacy Power BI formula:** `DIVIDE(SUM(cs[PP]), 5)`.
- **Proposed canonical formula:** считать `PP` напрямую на грейне (tournament, mapId, team),
  без денормализации на игроков.
- **Отличаются ли результаты:** да, на 5 из 448 карт (составы из 4 игроков вместо 5) — легаси
  формула даёт результат на 20% ниже истинного на этих картах.
- **Статус:** переносим с технической переработкой (см. `docs/powerbi_logic_audit.md` §4).

### `_TeamMatches` / `_TeamWins` / `_TeamLoses`

- **Legacy Power BI formula:** `DISTINCTCOUNT(cs[matchId])` (с фильтром по `w/l` для wins/loses).
- **Proposed canonical formula:** то же, но с явным требованием фильтра по одному турниру —
  `matchId` сбрасывается по турнирам (как и `mapId`), поэтому корректно **только** в
  контексте, ограниченном одним турниром.
- **Статус:** переносим с технической переработкой.

### `_RemainingMatches`

- **Legacy Power BI formula:** `6 - [_TeamMatches]`.
- **Proposed canonical formula:** нет — константа `6` не подтверждается ни на одном турнире
  (диапазон реальных значений matches-per-team — от 1 до 16, см.
  `artifacts/audit_v2/remaining_matches_audit.json`).
- **Решение для HTML-версии:** не переносить эту метрику без внешнего источника плановой сетки
  турнира (см. `docs/unresolved_questions.md` §2.1).
- **Статус:** legacy measure, требует решения пользователя.
