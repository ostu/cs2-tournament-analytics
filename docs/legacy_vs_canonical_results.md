# Legacy (Power BI) vs canonical — результаты сверки

Сравнение legacy-формул Power BI (`dax.txt`, разобраны в `docs/powerbi_logic_audit.md`) с
канонической моделью (`pipeline/build_marts.py`, `config/metric_definitions.json`), построенной
на реальных данных `data/raw/`. Числа — из `artifacts/audit_v2/*.json` (Audit v2) и из
самого пересчитанного pipeline (`data/processed/`, `artifacts/validation/validation.json`).

Принцип: расхождение не считается ошибкой канонической модели, если legacy-формула доказанно
некорректна (обоснование — в `docs/powerbi_logic_audit.md`).

---

## 1. `avgADR`

| | |
|---|---|
| Legacy formula | `_avgADR = AVERAGE(cs[adr])` |
| Canonical formula | `AVERAGE(adr WHERE adr_tracked=true)` |
| Затронутые строки | 1485 из 2235 строк (66.4%) карт, где ADR физически не собирался (турниры 1t-5t, 2c-5c) |
| Абсолютное расхождение (глобально) | 78.50 − 26.34 = **52.16** |
| Относительное расхождение | legacy занижает среднее ADR **в ~3 раза** |
| Причина | Legacy-формула усредняет ADR по ВСЕМ картам, включая те, где ADR не трекался (хранится как 0) — трактует "нет данных" как "0 урона за раунд". |
| Принятое решение | Каноническая формула считает среднее только по протрекованным картам; для игроков без ни одной протрекованной карты (35 из 84) публичный дашборд показывает "нет данных", не 0. |
| Что увидит пользователь в HTML | Колонка `ADR` с явным полем "покрытие ADR" (`adr_coverage`, %) рядом; при 0% покрытия — прочерк вместо числа. |

## 2. `avgKills` / `avgKills2`

| | |
|---|---|
| Legacy formula | `DIVIDE(SUM(cs[kills]), DISTINCTCOUNT(cs[mapId]))` (обе меры — подтверждённый дубль) |
| Canonical formula | `SUM(kills) / COUNT(DISTINCT (tournament_number, tournament_phase, map_number))` |
| Затронутые строки | Все 2235 строк факта (при контексте, охватывающем >1 турнир) |
| Абсолютное расхождение (глобально, все турниры) | legacy=1147.84, canonical=163.98 → разница **983.86** |
| Относительное расхождение | legacy завышает среднее **в ~7 раз** |
| Причина | `mapId` — не глобальный ключ, сбрасывается на каждом турнире (1..32 повторяются). `DISTINCTCOUNT(mapId)` в межтурнирном контексте считает уникальные ЗНАЧЕНИЯ (32), а не уникальные КАРТЫ (224). |
| Затронуто игроков (из 84) | 64 (76%) — знаменатель официальной формулы ниже канонического хотя бы на 1 |
| Принятое решение | Каноническая формула — единственная в HTML; legacy-версия не переносится ни в каком виде. |
| Что увидит пользователь в HTML | Колонка "Убийств/карту" — уже исправленное значение, без пометки "legacy" (формула Power BI была технически ошибочной, не альтернативной интерпретацией). |

## 3. `TeamsPP` (round differential команды)

| | |
|---|---|
| Legacy formula | `_TeamsPP = DIVIDE(SUM(cs[PP]), 5)` |
| Canonical formula | `round_diff`, посчитанный один раз на грейне (tournament, mapId, team) — без денормализации на игроков |
| Структурная проблема legacy-формулы | Делит на ЗАФИКСИРОВАННОЕ число 5 — корректно только если у команды на карте ровно 5 строк-игроков |
| Найдено карт с составом ≠ 5 в данных | 5 из 448 (団 team-map строк), т.е. 5 карт со составом из 4 игроков |
| Числовая демонстрация на реальных данных | **Не показана** — по совпадению все 5 карт с нестандартным составом также относятся к строкам, где сам счёт (`result`) не распознан (`result_parse_status=unparseable_date_like`), то есть `round_diff` для них `null` и в реальных данных сравнить `legacy/5` vs `canonical` числом не получилось. Структурная проблема формулы остаётся в силе независимо от этого совпадения. |
| Иллюстративный пример (синтетический, НЕ из реальных данных) | Команда выиграла карту с `round_diff=10`, но на карте было только 4 игрока: `legacy = (10×4)/5 = 8.0` (искажение −20%), `canonical = 10` (верно). |
| Принятое решение | Канонический `round_diff` считается напрямую на fact_team_map, не выводится из fact_player_map делением. |
| Что увидит пользователь в HTML | Колонка "Раундовый дифференциал" в профиле команды и в Team×Map — устойчива к любому размеру состава. |

## 4. `EloFinal`

| | |
|---|---|
| Legacy formula | `_EloFinal = SUM(tournaments[elo_calib]) + SUM(cs[elo_diff])` |
| Canonical formula | `elo_calib + Σelo_diff(rating_stage='t')` = событие `tournament_final` в `fact_player_rating_event` |
| Затронутые строки | 229 пар "игрок×турнир" (все 7 турниров) |
| Расхождение ПРИ корректном фильтре по стадии | **0** — точное совпадение с `players.t{n}_elo` на всех 7 турнирах (см. `artifacts/audit_v2/elofinal_legacy_vs_raw.json`, повторно подтверждено в `artifacts/validation/validation.json` → `rating_after_equals_before_plus_change`) |
| Расхождение БЕЗ фильтра по стадии (если `elo_diff` не разделять на calib/tournament) | до **780** очков на игрока |
| Причина риска | `tournaments`/`cs` в Power BI не разделяют `tournament_number` и `rating_stage` как отдельные поля — легко просуммировать `elo_diff` калибровки и турнира вместе по ошибке. |
| Принятое решение | В канонической модели `rating_stage` — отдельное, обязательное поле на каждом событии; агрегация по ошибке невозможна без явного игнорирования этого поля. |
| Что увидит пользователь в HTML | `EloFinal` — то же число, что было бы у корректно настроенной DAX-меры; никакой замены/оговорки не требуется (формула была правильной при правильном использовании, теперь используется правильно всегда). |

## 5. `startElo`

| | |
|---|---|
| Legacy formula | `_startElo = CALCULATE(SUM(tournaments[elo_start]), FILTER(tournaments, tournaments[Tournament]=MIN(tournaments[Tournament])))` |
| Canonical formula | `MIN(tournament_number)` (числовое), затем `rating_after` события `normalized_entry` этого турнира |
| Затронутые строки | Латентно — 0 на данный момент (турниры только 1-9, однозначные номера); риск проявится с турнира №10 |
| Расхождение на текущих данных | **0** — `tournaments[Tournament]` в формате `"t1".."t7"`, лексикографический `MIN` совпадает с числовым при однозначных номерах |
| Причина риска | `tournaments[Tournament]` — текстовое поле; `"t10" < "t2"` как строки, что даст неверный `MIN` при появлении турнира №10+ |
| Принятое решение | Каноническая модель использует числовой `tournament_number` везде, где нужен `MIN`/`MAX`/сортировка — риск снят на будущее, не только для текущих 7 турниров. |
| Что увидит пользователь в HTML | Не отличается сейчас; станет отличаться (в лучшую сторону) при добавлении турнира №10. |

## 6. Простые агрегаты (kills/deaths/K-D) — сверка "как есть"

Прямые суммы (`kills`, `assists`, `deaths`) и производные от них (`K/D`, `K/R`) НЕ являются
предметом спора между legacy и canonical — расхождение возникает только там, где легаси-формула
использует испорченный знаменатель (`avgKills`) или неподтверждённое усреднение (`ADR`). Прямая
проверка (пример — игрок с наибольшим числом карт, обозначен здесь как `Player-Alpha`, реальный игровой идентификатор анонимизирован в этом документе):

| Метрика | mart_player_summary | Прямая сумма по `data/raw/cs_farpost_tournament_results.xlsx` |
|---|---|---|
| kills | 2160 | 2160 |
| deaths | 1534 | 1534 |
| K/D | 1.40808... | 1.40808... (kills/deaths посчитано вручную) |

Совпадает точно — подтверждает, что каноническая модель не меняет сами исходные счётчики, только
способ агрегации там, где легаси-формула была структурно неверна.
