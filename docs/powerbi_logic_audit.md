### 1.7 `cs2_team_score` / `cs2_team_score_2`

Две почти идентичные таблицы, вместе образующие **симметричную пару "команда/соперник"**:

| | `cs2_team_score` (`_1`) | `cs2_team_score_2` (`_2`) |
|---|---|---|
| Источник | `cs` | `cs` |
| Поля | `matchId, mapId, map, result, w/l, team, Tournament` | то же |
| Pivot | `w/l` (значения) × `team` (столбцы) → строка на карту с колонками `W`/`L` = имена команд | то же |
| Доп. преобразования | `matchId` → `"m"+matchId+"_1"`, `w/l` перезаписан константой `1` | `matchId` → `"m"+matchId+"_2"`, `w/l` перезаписан константой `2`, **колонки `W`/`L` переименованы друг в друга** (инверсия), `result` **развёрнут** (`"17-19"` вместо `"19-17"`) |
| Итоговый grain | карта (одна строка на матч/карту) | карта, но с инвертированной точкой зрения |
| Append | `cs2_team_score = Combine({свой результат, cs2_team_score_2})` | — |

**Смысл:** это построение таблицы, где для каждой карты существуют ДВЕ строки — одна с точки
зрения победителя, вторая с точки зрения проигравшего (с обратным именем в колонке "своя
команда" и обратным счётом) — то есть визуал (вероятно, Team×Map матрица/тултип) может искать
"свою" команду в одной и той же колонке независимо от исхода матча. Это прямо объясняет меру
`_result_and_map`, которая берёт `result`/`map` из `cs2_team_score` через `FIRSTNONBLANK`.

| | |
|---|---|
| Источник | `cs` |
| Вычисляемые поля | `Tournament_mapId-map = Tournament&"_"&Text.PadStart(mapId,2,"0")&"_"&map` |

| Потребители | вероятно, waterfall-визуал прогресса Elo игрока (включая стадии `a`/`n`), напрямую, без отдельной DAX-меры — ни одна мера в `dax.txt` не ссылается на `player_elo_diff` |

## 2. `mapId + 1` — детальный разбор (см. `artifacts/audit_v2/mapid_offset_audit.json`)

**Почему сдвиг существует:** `cs_farpost_elo_changes.mapId` начинается с **0** в каждом турнире
(итог `range(max_mapId)` — 0-based цикл в `cs_farpost_tournament.ipynb`, ячейка 3), тогда как
`cs_farpost_tournament_results.mapId` начинается с **1**. Подтверждено на всех 13
турнирах/калибровках без исключения (`elo_changes.groupby('tournament')['mapId'].min()` == 0
везде; `tournament_results` — везде 1).

**Это коррекция 0-based/1-based индексации, а не смысловой перенос на предыдущую/следующую
карту.**

**Результат сдвига на реальных данных:**
- со сдвигом (`mapId+1`): **2234 из 2235** строк `tournament_results` получают `elo_diff`
  (99.96%);
- без сдвига: только **1067 из 2235** (47.7%) — то есть без `+1` данные были бы наполовину
  несвязаны;
- "осиротевших" строк `elo_changes` (без сдвигом они не находят пару и по прямому счёту тоже
  не должны) — **0**;
- **первая карта каждого турнира не теряется** — вопреки интуитивному предположению, что
  сдвиг "отрезает" первую или последнюю карту, все 130 строк с `mapId==1` успешно находят
  пару (потому что `elo_changes` для этой же карты имеет исходный `mapId=0`, который после
  `+1` становится `1`).
- **1 не сматченная строка** на весь датасет: `tournament=5t, mapId=10, id=Player-Gamma`
  (идентификатор анонимизирован), `team=РашА` — в `cs_farpost_elo_changes.xlsx` для тур. 5t на 1 строку меньше, чем в
  `tournament_results` (197 против 198) — вероятно, единичный пропуск при экспорте.

**Вывод:** сдвиг корректен и необходим для соединения этих двух таблиц именно в имеющемся
виде. Он не был "автоматически перенесён" в предложенную ниже каноническую модель — вместо
этого предлагается хранить `mapId` в `fact_player_rating_event` уже выровненным (1-based,
как в `tournament_results`) на этапе построения витрины, чтобы сдвиг не был скрытой магией
внутри Power Query, а был явным шагом трансформации с комментарием.

## 3. `result` / счёт — детальный разбор (см. `artifacts/audit_v2/result_score_audit.json`)

| Класс | Количество строк | Доля |
|---|---|---|
| `valid_score` (`"N-N"`) | 450 | 20.1% |
| `date_like_excel_corruption` | 1785 | 79.9% |
| `empty` / `other` | 0 | 0% |

Для `valid_score`: `r1+r2 == rounds` в **100%** случаев (450 из 450) — подтверждает, что счёт и
число раундов согласованы, когда счёт сохранился как текст.

Для `date_like_excel_corruption` (например `2022-07-16 00:00:00`):
- месяц всегда 1–12, день всегда **13 или 16** (никаких других значений дня);
- `месяц + день == rounds` совпадает в **98.9%** случаев (1766 из 1785; 19 расходящихся строк —
  всё из турнира `1t`, `mapId` 8 и 10, `rounds=22` против `month+day=24`);
- год испорченной даты **точно совпадает с реальным календарным годом турнира** (`1t/2c/2t` →
  2022, `3c/3t` → 2023, ..., `7c/7t` → 2026).

**Заключение:** это практически наверняка не мусорные данные, а счёт карты формата `"M-D"` или
`"D-M"`, где одно число ≤12 (Excel читает как месяц) и другое ≥13 (Excel читает как день), и
Excel автоматически конвертировал такую текстовую ячейку в дату при вводе/сохранении, подставив
текущий на тот момент год. Это объясняет, почему в предоставленном `data/raw/*.xlsx`
(предположительно прошедшем через Excel) эта проблема есть, а в живом Google Sheets CSV,
который читает Power Query, её, возможно, и нет — **не проверено сетевым запросом**, только
выведено из внутренней согласованности (год/месяц/день) данных, которые у нас есть.

**Восстановление исходного счёта возможно** с одним ограничением: месяц/день дают МНОЖЕСТВО
`{a,b}` двух чисел счёта, но не порядок (кто именно выиграл с каким числом) — это нужно
дополнительно сверять с `w/l` (у победителя число раундов не может быть меньше, чем у
проигравшего, за исключением редких особых правил). Восстановление **не выполнялось** в этом
отчёте (это уже шаг построения витрины, не аудита) — решение остаётся на этап моделирования.

## 4. `PP` — детальный разбор (см. `artifacts/audit_v2/pp_roster_audit.json`)

**Формула:** `PP = if [w/l]="W" then [r1]-[r2] else [r2]-[r1]`, где `r1`/`r2` — первое и второе
число распарсенного `result`. Так как `r1`/`r2` не зависят от того, какая это строка (не "своя
команда/чужая", а фиксированный порядок из текста счёта), результат:
- для строки победителя: `r1 - r2` (положительная величина, если счёт в тексте пишется
  "выигравшая-проигравшая");
- для строки проигравшего: `r2 - r1` (тоже положительная по модулю, но с обратным знаком в
  сумме, если `r1`/`r2` не переставлять).

**PP хранится на грейне игрок×карта, но по значению — это метрика команда×карта**: значение
идентично для всех игроков одной команды на одной карте (не индивидуальный показатель).

**Почему `_TeamsPP` делит на 5:** `SUM(cs[PP])` по всем строкам состава команды на карте
складывает одно и то же число 5 раз (по разу на каждого игрока) — деление на 5 компенсирует
это дублирование и возвращает истинный "раундовый дифференциал" карты/набора карт.

**Проверка допущения "5 игроков в составе":** 443 из 448 комбинаций (tournament, mapId, team)
имеют ровно 5 строк-игроков; **5 комбинаций имеют 4** (`1t/mapId8/Gambot`,
`1t/mapId24/RunChickenRun`, `1t/mapId26/sweaty dumpling`, `5t/mapId9/ГдеБомба?`,
`5t/mapId9/Плотина Крутых Бобров`). Для этих 5 карт деление на константу 5 даёт **на 20%
заниженный** результат относительно того, что дало бы деление на фактический размер состава (4).

**Каноническая альтернатива:** считать раундовый дифференциал напрямую на грейне
`(tournament, mapId, team)` — по одному значению на карту, без денормализации на игроков и без
деления на захардкоженную константу. Устойчиво при любом фактическом размере состава.

## 5. `tMapIndex` — детальный разбор

**Формула** (`cs`, ячейка `Added Custom1`):

```
tMapIndex = Text.Range(Tournament, 0, len(Tournament)-1)          -- номер турнира без буквы стадии
          & (if Text.Range(Tournament, len-1) = "t" then "2" else "1")  -- 2=основной турнир, 1=калибровка
          & Number.ToText(mapId, "00")                             -- mapId, дополненный нулём до 2 знаков
```

Пример: `Tournament="8t", mapId=5` → `tMapIndex = "8" & "2" & "05" = "8205"`.
`Tournament="8c", mapId=3` → `tMapIndex = "8" & "1" & "03" = "8103"`.

**Назначение:** единый сортируемый ключ, где калибровочные карты турнира N (средняя цифра `1`)
всегда сортируются раньше основных карт того же турнира N (средняя цифра `2`) — используется в
`_tournamentEloDiff` как условие `cs[tMapIndex] <= MAX(cs[tMapIndex])` для накопительной суммы
(waterfall/running total) **в рамках одного турнирного цикла**.

**Ограничения:**
1. Номер турнира **не дополняется нулями** — для турниров 1-9 это 1 символ, для турнира ≥10 —
   2 символа. Из-за этого при текстовом (лексикографическом) сравнении `tMapIndex` турнира 10
   (например `"10205"`) может оказаться **меньше** `tMapIndex` турнира 1 с картой 20+
   (`"1205"` < `"10205"` неверно упорядочены как строки: `"10205" < "1205"`, потому что `'0' <
   '2'` на второй позиции). Это станет реальной проблемой, как только появится турнир №10 —
   сейчас (турниры 1-7) скрытая, непроявившаяся ошибка.
2. `tMapIndex` считается только для строк `cs` (то есть только там, где есть `mapId` — стадии
   `a`/`n` в него не попадают, так как `elo_norm` не участвует в построении `cs`).

**Предлагаемая замена** (без изменения текущих данных, только для новой модели):
явные числовые поля `tournament_number` (без строкового дополнения) + `rating_stage_order`
(10/20/30/40 из `docs/rating_semantics.md`) + `map_sequence` (`mapId`, уже 1-based) +
единый `rating_event_sequence` = `tournament_number * 1000 + rating_stage_order * 10 +
map_sequence` (числовое, а не текстовое поле — сортируется корректно при любом количестве
цифр в `tournament_number`).

## 6. Полный разбор DAX-мер

| Мера | Формула | Grain/filter context | Бизнес-смысл | Проблемы | Python-эквивалент | Статус |
|---|---|---|---|---|---|---|
| `_avgADR` | `AVERAGE(cs[adr])` | любой (обычно игрок/команда/турнир) | средний урон за раунд | включает untracked-нули (66% строк в среднем по всем турнирам, 100% в 1t-5t/2c-5c) — искусственно занижает при смешивании с "не собиралось" | `df.loc[df.adr_tracked, 'adr'].mean()` (availability-aware) | требует решения пользователя |
| `_avgKills` | `DIVIDE(SUM(cs[kills]), DISTINCTCOUNT(cs[mapId]))` | любой | среднее убийств за карту | `mapId` не глобальный ключ (сбрасывается на каждом турнире) — при контексте >1 турнира знаменатель занижен (глобально: 32 вместо 224, т.е. avgKills завышен в ~7 раз: 1147.8 против 163.98) | `kills.sum() / results[['tournament','mapId']].drop_duplicates().shape[0]` | переносим с технической переработкой |
| `_avgKills2` | идентична `_avgKills` | то же | **подтверждённый полный дубль** `_avgKills` (побайтово одинаковая формула в `dax.txt`) | то же + сам факт дублирования — legacy-имя, вероятно от копипаста | тот же | legacy measure (оставить как алиас канонической `avgKills`, не отдельную метрику) |
| `_KD` | `DIVIDE(SUM(cs[kills]), SUM(cs[deaths]))` | любой | Kills/Deaths, сумма-к-сумме | `DIVIDE` возвращает `BLANK()` при `deaths=0` — само по себе не баг, но нужно явное решение для HTML (показывать "—"?) | `kills.sum()/deaths.sum() if deaths.sum() else None` | переносим без изменений |
| `_KD2` | идентична `_KD` | то же | **подтверждённый полный дубль** | то же | тот же | legacy measure |
| `_KR` | `DIVIDE(SUM(cs[kills]), SUM(cs[rounds]))` | любой | Kills/Round, сумма-к-сумме | нет искажающих факторов (в отличие от `_avgKills`, тут нет проблемы сброса ключа — `rounds` суммируется корректно на любом гране) | `kills.sum()/rounds.sum()` | переносим без изменений |
| `_KR2` | идентична `_KR` | то же | **подтверждённый полный дубль** | то же | тот же | legacy measure |
| `_elo_diff` | `SUM(cs[elo_diff])` | любой | сумма изменения Elo по картам (после join `mapId+1`) | наследует ограничения сдвига `mapId+1` (1 несматченная строка на весь датасет — незначимо) | `elo_diff.sum()` по отфильтрованным строкам `cs` | переносим без изменений |
| `_elo_diff%` | `DIVIDE([_elo_diff], SUM(tournaments[elo_calib]))` | игрок × турнир (нужен `tournaments`) | относительное изменение Elo относительно `elo_calib` (`Nc`) | база подтверждена (`elo_calib`), но зависит от корректного джойна `cs`↔`tournaments` через team/tournament ключи | `elo_diff_sum / elo_calib_sum` | переносим без изменений (база теперь подтверждена) |
| `_EloFinal` | `SUM(tournaments[elo_calib]) + SUM(cs[elo_diff])` | игрок × турнир | итоговый Elo турнира (`Nt`) | точно совпадает с `players.t{n}_elo`, ЕСЛИ `elo_diff` фильтруется только по `rating_stage='t'` (см. `docs/rating_semantics.md` §5); без этого фильтра — расхождение до ~780 очков | `elo_calib + elo_diff[stage=='t'].sum()` | переносим с технической переработкой (явный фильтр по stage) |
| `_tournamentEloDiff` | `[_startElo] + CALCULATE(SUM(cs[elo_diff]), cs[tMapIndex]<=MAX(cs[tMapIndex]))` | карта (для waterfall/running total) | накопительный Elo от начала турнира до текущей карты | зависит от `tMapIndex` (см. §5, ограничение для турниров ≥10) и от `_startElo` (см. ниже, лексикографический `MIN`) | накопительная сумма по `rating_event_sequence` в отсортированном порядке | переносим с технической переработкой |
| `_result_and_map` | `CONCATENATE(CONCATENATE(FIRSTNONBLANK(cs2_team_score[result],1),UNICHAR(10)),FIRSTNONBLANK(cs2_team_score[map],1))` | карта (тултип) | текст "счёт\nкарта" для тултипа/подписи | зависит от `cs2_team_score`'s инвертированной пары строк (см. §1.7) — не является ошибкой, а сознательным приёмом | `f"{result}\n{map}"` на нужной строке | переносим без изменений |
| `_RemainingMatches` | `6 - [_TeamMatches]` | команда × турнир | "сколько матчей осталось" при жёстко зашитом плане в 6 матчей | **допущение не подтверждается**: matches-per-team-per-tournament варьируется от 1 до 16 (см. §7 ниже) — 6 не универсально | нет универсального эквивалента без источника расписания | legacy measure / требует решения пользователя |
| `_TeamMatches` | `CALCULATE(DISTINCTCOUNT(cs[matchId]))` | команда (+ подразумеваемый турнир в контексте) | число уникальных матчей команды | `matchId` сбрасывается по турнирам, как и `mapId` — корректно ТОЛЬКО если контекст уже ограничен одним турниром | `results[results.team==T].groupby('tournament')['matchId'].nunique()` | переносим с технической переработкой (явно требовать фильтр по турниру) |
| `_TeamWins` | `CALCULATE(DISTINCTCOUNT(cs[matchId]), cs[w/l]="W")`, 0 если `BLANK` | команда × турнир | число побед | то же ограничение по `matchId`, что у `_TeamMatches` | аналогично | переносим с технической переработкой |
| `_TeamLoses` | `CALCULATE(DISTINCTCOUNT(cs[matchId]), cs[w/l]="L")`, 0 если `BLANK` | команда × турнир | число поражений | то же | аналогично | переносим с технической переработкой |
| `_TeamsPP` | `DIVIDE(SUM(cs[PP]),5)` | команда (× карта/турнир) | раундовый дифференциал команды | денормализация "÷5" ломается на 5 из 448 карт с составом из 4 игроков (см. §4) | считать PP напрямую на грейне (tournament,mapId,team), без денормализации | переносим с технической переработкой |
| `_startElo` | `CALCULATE(SUM(tournaments[elo_start]), FILTER(tournaments, tournaments[Tournament]=MIN(tournaments[Tournament])))` | игрок (в текущем фильтре по турнирам) | `elo_start` самого раннего турнира игрока в текущем контексте | `tournaments[Tournament]` — текстовое `"t1".."t7"`; лексикографический `MIN` ломается при турнире ≥10 (`"t10" < "t2"` как строки) — см. §8 ниже | `elo_start` при `tournament_number == min(tournament_number)` (числовое сравнение) | переносим с технической переработкой |

### Duplicate measures — итог

Подтверждено текстовым сравнением формул в `dax.txt` (побайтовое совпадение выражений):

- `_avgKills` ≡ `_avgKills2`
- `_KD` ≡ `_KD2`
- `_KR` ≡ `_KR2`

**Решение для новой модели:** оставить одну каноническую метрику на каждую пару (`avgKills`,
`KD`, `KR`), задокументировать `_avgKills2`/`_KD2`/`_KR2` как legacy-алиасы (на случай, если
какой-то внешний потребитель ссылается на старое имя), не реализовывать их отдельно.

## 7. `_RemainingMatches` = `6 - _TeamMatches` — проверка допущения

`artifacts/audit_v2/remaining_matches_audit.json`. Matches-per-team-per-tournament (только
основные турниры, суффикс `t`):

| Турнир | mean | min | max |
|---|---|---|---|
| 1t | 3.7 | 2 | 5 |
| 2t | 7.1 | 6 | 8 |
| 3t | 5.0 | 5 | 5 |
| 4t | 5.6 | 4 | 6 |
| 5t | 5.6 | 4 | 6 |
| 6t | 4.0 | 3 | 5 |
| 7t | 7.4 | 6 | 9 |

Калибровки (`c`) варьируются ещё сильнее — от 1 (2c) до 16 (6c) матчей на команду. **Ни один

матчей per-турнир из внешнего источника (расписание/сетка), либо не переносить эту метрику.

## 8. `_startElo` = `MIN(tournaments[Tournament])` — проверка допущения

`tournaments[Tournament]` — текст в формате `"t1".."t7"` (см. §1.8). Лексикографический `MIN`:
- корректен для однозначных номеров (`"t1" < "t2" < ... < "t9"`);
- **некорректен**, как только появится турнир №10+: строка `"t10"` меньше `"t2"` (сравнение
  символ за символом: `'1' < '2'`), значит `MIN(...)` вернул бы `"t10"` вместо реально самого
  раннего `"t1"`, если оба присутствуют в контексте.

**Предлагаемая замена:** вычислять `MIN(tournament_number)` как число (не по колонке
`tournaments[Tournament]` как тексту), затем брать `elo_start` для этого числового минимума.
