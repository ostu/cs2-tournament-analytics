# Privacy & Publication Contract — Audit v2

Публичная HTML-версия дашборда **не должна** содержать настоящих идентификаторов игроков.
Статистика (kills/ADR/Elo/места и т.п.) остаётся реальной — псевдонимизируется только то, что
указывает на конкретного человека.

Этот документ — спецификация архитектуры и её реализация (Audit v3): `pipeline/build_public_data.py`
строит `data/public/*.json`, `pipeline/build_dashboard.py` собирает из них `dashboard.html`.

---

## 0. Найденная реальная утечка: название команды = private id игрока

При первом прогоне `check_publication_leaks.py` на `data/public/` обнаружено настоящее
совпадение (не ложное срабатывание): название одной исторической команды буквально содержало
как подстроку `id`/`steam_name` одного из игроков (команда, судя по всему, была названа в честь
этого игрока). **Конкретное название команды и идентификатор игрока не приводятся в этом
документе намеренно** — сам факт их сочетания и есть та утечка, которую нужно было устранить;
приводить пример означало бы воспроизвести проблему в документации, которая сама готовится к
публикации. Хотя названия команд в целом разрешены к публикации (раздел 1 ниже), в этом
конкретном случае публикация имени команды деанонимизировала бы именно этого игрока через
состав команды, обходя псевдонимизацию.

**Решение:** `pipeline/build_public_data.py::build_team_redaction_map()` перед экспортом
проверяет КАЖДОЕ каноническое имя команды на вхождение любого приватного токена (той же
проверкой, что использует `check_publication_leaks.py`) и заменяет совпавшие имена на
детерминированный плейсхолдер (`"Команда (имя скрыто #N)"`, нумерация по отсортированному
списку команд) — везде, где это имя встречается (сама команда, `opponent_team_key` у соперников,
`latest_team` у игроков). Замена не хранит обратимой связи с исходным именем. Найденный случай
выводится в консоль сборки (не публикуется), чтобы решение было видно, а не скрыто молча.
Итог на момент написания: **1 из 69** команд потребовала такой замены.

## 1. Запрещённые в публичной сборке значения

Никогда не должны появляться в HTML, встроенном JSON, tooltip, DOM-атрибутах, URL, именах
файлов или логах публичной сборки:

- `steam_name`
- `id` (внутренний slug-идентификатор игрока)
- `player_id`
- `steam_account`
- `discord_name`
- `faceit_name`, `faceit_link`
- `fio`
- `city`, `department`
- `another_names`
- любые ссылки на аккаунты (Steam/Faceit/Discord)

**Названия команд НЕ входят в этот список** — команда не идентифицирует конкретного человека
напрямую (это единица турнира, не персональные данные), и по условиям задачи публичный
дашборд должен показывать реальные результаты по командам. Если у пользователя другие
пожелания насчёт команд — уточнить отдельно.

## 2. Архитектура `data/private/player_aliases.csv`

Реализована в `pipeline/generate_player_aliases.py`; таблица создана в
`data/private/player_aliases.csv` (не в git — см. `.gitignore`).

| Поле | Смысл |
|---|---|
| `private_player_key` | реальный внутренний идентификатор (колонка `id` из `players.xlsx`) |
| `public_player_id` | стабильный opaque-код вида `P-a1b2c3d4` (случайный, `secrets.token_hex`) |
| `public_nickname` | человекочитаемый псевдоним вида `"Quiet Falcon"` (случайная пара adjective+noun) |
| `created_at` | ISO-таймстемп первого присвоения |

Свойства (проверены в `pipeline/generate_player_aliases.py`):

- **Создаётся один раз, дополняется идемпотентно.** Скрипт при повторном запуске не трогает
  уже присвоенные псевдонимы — только добавляет новых игроков, которых ещё нет в таблице
  (проверено: второй запуск на тех же 86 игроках добавил 0 новых строк).
- **Один игрок — один псевдоним во всех турнирах.** Псевдоним привязан к `private_player_key`,
  а не к паре (игрок, турнир) — при джойне на любую турнирную/матчевую таблицу подстановка
  всегда даёт то же самое публичное имя.
- **Без коллизий.** Генератор проверяет уникальность `public_player_id` и `public_nickname`
  перед перегенерацией кандидата; после записи файла — `assert` на отсутствие дублей.
- **Не в git.** `data/private/` в `.gitignore`; проверено (`git check-ignore -v
  data/private/player_aliases.csv` подтверждает игнор).
- **Не попадает в финальный HTML.** Файл используется только на этапе ПОСТРОЕНИЯ публичной
  витрины (заменить `id`/`steam_name` на `public_nickname` перед сериализацией в
  JSON/HTML) — сам файл в публичную сборку не копируется.
- **Псевдоним не является обратимым открытым hash'ем.** `public_player_id`/`public_nickname`
  генерируются случайно (`secrets`/`random`), а не как функция от `private_player_key`
  (например, не `sha256(id)[:8]`) — при небольшом и известном множестве реальных id
  (86 игроков) усечённый хеш был бы тривиально подобран по словарю (rainbow-table атака на
  замкнутое множество кандидатов), то есть не давал бы реальной анонимности, даже будучи
  криптографически "необратимым" в общем случае. Случайное присвоение с хранением в приватной
  таблице снимает эту проблему: восстановить псевдоним по `id` можно только имея сам файл
  `data/private/player_aliases.csv`.

## 3. Автоматическая проверка утечек

Реализована в `pipeline/check_publication_leaks.py`.

**Принцип:**
1. Собрать множество всех известных реальных идентификаторов/PII из `data/raw/` (`id`,
   `player_id`, `steam_name`, `steam_account`, `fio`, `city`, `department`, `discord_name`,
   `faceit_name`, `faceit_link`, `another_names`) + `private_player_key` из
   `data/private/player_aliases.csv`.
2. Рекурсивно обойти указанную директорию будущей публичной сборки, проверить **и содержимое
   файлов, и сами имена файлов** на буквальное вхождение любого из этих значений
   (регистронезависимо).
3. Если найдено хотя бы одно совпадение — вывести список находок (файл, где найдено:
   имя файла/содержимое, какой токен) и завершиться с ненулевым кодом возврата.

**Запуск:**
```
python pipeline/check_publication_leaks.py <путь_к_папке_публичной_сборки>
python pipeline/check_publication_leaks.py --self-test
```

`--self-test` прогоняет механизм на временных файлах (создаёт чистый и "утечный" HTML во
временной директории) и проверяет, что чистый файл проходит, а утечный — детектируется и в
имени файла, и в содержимом. **Пройден при написании этого документа.**

**Обязательное условие перед публикацией (следующий этап проекта):** запуск
`check_publication_leaks.py` на итоговой директории публичной сборки должен завершиться кодом
`0`, иначе публикация не выполняется. Это соответствует требованию задания "пока не создавай
финальный публичный набор без отдельной проверки утечек".

**Известные ограничения самого чекера** (честно, не скрываем):
- Ловит только **буквальные** совпадения (с учётом регистра неважно) — не поймает, например,
  транслитерацию или обфусцированное написание идентификатора внутри сжатого/минифицированного
  JS, если оно составлено конкатенацией строк в рантайме браузера (статический грep этого не
  увидит). Для полной уверенности перед первой публикацией имеет смысл дополнительно вручную
  просмотреть итоговый bundle.
- Не проверяет бинарные форматы (изображения, шрифты) — если в них случайно зашито имя (напр.,
  скриншот с реальным ником), чекер это не обнаружит.

## 5. Процесс публикации (для следующего этапа, не реализуется сейчас)

1. Построить публичные `mart_*`-таблицы, где вместо `id`/`steam_name` используется
   `public_nickname` (джойн через `data/private/player_aliases.csv`, который сам не копируется
   в публичную директорию).
2. Убедиться, что ни team-профиль, ни tooltip, ни URL/имена файлов не содержат `private_player_key`
   или любое поле из списка запрещённых (раздел 1) — например, не создавать файлы вида
   `player_<id>.html`, использовать `public_player_id` в путях.
3. Прогнать `pipeline/check_publication_leaks.py <build_dir>` — публикация продолжается только
   при коде возврата `0`.
4. Только после успешной проверки — публикация (в этом проекте: следующий этап, статический
   HTML).
