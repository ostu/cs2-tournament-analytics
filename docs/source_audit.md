## 1. Executive summary

- Репозиторий содержит **5 таблиц Excel** в `data/raw/` и **2 Jupyter/Colab-тетради** в корне
  проекта. Никаких других конфигов, скриптов, README или документации в проекте не было —
  весь контекст расчётов существует только в notebook-коде и в головах авторов Power BI отчёта.
- Все 5 таблиц читаются без ошибок, полных дублей строк нет, гипотетические ключи по каждой
  таблице подтвердились как уникальные (см. раздел 3).
- Две тетради — это **не production-пайплайн**, а рабочий шаблон, который **вручную
  редактировался и запускался по одному разу на каждый турнир/калибровку** (константы
  `TOURNAMENT`, `ELO_CALIB`, `ELO_START` задаются в коде руками). Итоговые файлы
  `cs_farpost_elo_changes.xlsx` и `cs_farpost_elo_norm.xlsx` — это, по всей видимости,
  накопленный вручную результат многих таких запусков, а не воспроизводимый батч-процесс.
- Часть метрик, видимых на скриншотах Power BI (`KD`, `KR`, `avgKills2`, `elo_diff%`, рейтинги
  игроков/команд), **не имеет ни одной строки кода в notebook-файлах и не является колонкой ни
  в одной исходной таблице**. Эти метрики рассчитывались, скорее всего, в DAX/Power Query —
  подтверждённой формулы для них нет (см. `docs/metric_catalog.md` и раздел 7 ниже).
- Найдены реальные проблемы качества данных: расхождения в написании названий команд
  (`Мидоеды`/`мИдоеды`, `Brainrot`/`brainrot`, `RunChickenRun`/`RunChiken­Run`, эмодзи-обёртки
  вокруг названий), смешанный тип в колонке `result` (даты и строки-счёт `"19-17"`), таблица
  игроков содержит персональные данные (ФИО, город, департамент, Discord/Faceit-ссылки).
- Ничего в `data/raw/` не менялось: скрипт только читает файлы, контрольные суммы SHA-256
  зафиксированы в `artifacts/data_profile/checksums.json`.

## 3. Описание каждой таблицы

Все файлы — `.xlsx` (OOXML/zip), поэтому понятия "кодировка текстового файла" и "разделитель"
к ним неприменимы (это не CSV). Имена листов внутри файлов отображаются как один лист с
кириллическим названием (`Лист1`), которое ломается в консоли Windows/cp1251 — это чисто
терминальный артефакт, не проблема данных.

### 3.1 `cs_farpost_elo_changes.xlsx`

| | |
|---|---|
| Строк / колонок | 2234 / 4 |
| Колонки | `id`, `mapId`, `elo_diff`, `tournament` |
| Грануляция | игрок × карта × турнир |
| Ключ | `(id, mapId, tournament)` — уникален, дублей 0 |
| tournament, значения | `1t,2c,2t,3c,3t,4c,4t,5c,5t,6c,6t,7c,7t` (13 турниров/калибровок, номера 1–7) |
| Игроков | 84 уникальных `id` |

`mapId` — **не глобальный** номер карты, а порядковый номер карты внутри конкретного
турнира (сбрасывается на каждом турнире, как и в `cs_farpost_tournament_results.xlsx`).
Формат `id` — латинский slug (примеры формата, не реальные значения: `player-slug-1`,
`player-slug-2`), совпадает с колонкой `id` в
`cs_farpost_players.xlsx` (полная referential integrity: все `id` из этой таблицы есть в
players).

### 3.2 `cs_farpost_elo_norm.xlsx`

| | |
|---|---|
| Строк / колонок | 266 / 3 |
| Колонки | `id`, `elo_diff`, `tournament` |
| Грануляция | игрок × "вход в турнир" |
| Ключ | `(id, tournament)` — уникален |
| tournament, значения | `1a..7a` (7 штук) **и один аномальный код `7n`** |

Суффикс `a` соответствует функции `build_elo_diff_table` из `cs_farpost_tournament.ipynb`

всегда генерирует только суффикс `a`) — 36 строк с `tournament == "7n"` содержат тот же
набор `id`, что и `7a`, но другие значения `elo_diff`. Это не объясняется ни одним из
notebook-файлов — вероятно, ручная пост-обработка/повторная нормализация после турнира 7.
**Требует уточнения у владельца отчёта** (см. раздел 9).

### 3.3 `cs_farpost_players.xlsx`

| | |
|---|---|
| Строк / колонок | 86 / 54 |
| Ключ | `id` и `player_id` — оба уникальны |
| Грануляция | один игрок |

Структура колонок:

  steam_account, fio, steam_name, another_names`. **`fio` (ФИО), `city`, `department`,
  `discord_name` — персональные данные сотрудников компании** (по названиям департаментов —
  это внутренний корпоративный турнир). `city`/`department`/`faceit_*` пустые в ~51–68 строках

- По каждому турниру `t1`…`t7` — блок из 3 колонок: `t{n}_team`, `t{n}_elo_start`,

  **Команда — атрибут пары (игрок, турнир), а не игрока в целом**: один и тот же `id` в
  разных `t{n}_team` может состоять в разных командах.
- `Unnamed: 39` — бинарный флаг (`1`/`NaN`), назначение не установлено по имеющимся данным.
- `map1`…`map13` — **не карты CS2**, а флаги участия в конкретном калибровочном матче (судя по

  фильтру отбираются ровно 10 игроков для деления на 2 команды по 5). Сумма `1` в каждой из
  колонок `map1..map13` равна ровно 10 — это подтверждает гипотезу (10 участников на
  калибровочный матч).
- `Unnamed: 53` — числовое поле 2–10; **подтверждено эмпирически**, что оно равно построчной
  сумме `map1..map13` (количеству калибровочных матчей, в которых участвовал игрок). Это
  избыточная/производная колонка.

  нулевых ADR в дефолтных/технических матчах — статистически подозрительно, стоит уточнить.
- `headshots, headshots_percent, triple_kills, quadro_kills, penta_kills` — заполнены только
  у 297 из 2235 строк (остальные `NaN`), то есть эти показатели трекались лишь в части
  турниров/выгрузок.
- `date` — при чтении через `pd.read_csv` в notebook строки дат приходили в формате
  `05/04/26` (буквенно неоднозначный день/месяц/год); в текущем `.xlsx` они уже приведены к

## 4. Описание notebook-файлов

Обе тетради читают одни и те же два публичных Google Sheets CSV-экспорта (сетевые запросы,
без Colab-специфичного API типа `google.colab.drive` — то есть формальной привязки к Colab
нет, это обычный `pandas.read_csv` по URL, который может выполняться в любом Jupyter/Python):

```python
players   = pd.read_csv("https://docs.google.com/spreadsheets/.../pub?...output=csv")
t_results = pd.read_csv("https://docs.google.com/spreadsheets/.../pub?...output=csv")
```

По содержимому это тот же материал, что лежит в `cs_farpost_players.xlsx` и
`cs_farpost_tournament_results.xlsx` (совпадают колонки, включая специфичные вроде `t{n}_team`
или `triple_kills`). **Мы не выполняли эти сетевые запросы** (нельзя проверять сеть по
условиям задания) — совпадение установлено по структуре, а не байт-в-байт.

### 4.1 `cs_farpost_tournament.ipynb` (6 ячеек)

| Ячейка | Тип | Назначение |
|---|---|---|
| 0 | код | импорты (`re`, `pandas`, `math`) |
| 1 | markdown | описание источников (ссылки на Google Sheets) |
| 2 | код | загрузка `players`, `t_results` из CSV |
| 3 | код, **production** | расчёт `elo_diff` по картам для одного турнира → `elo_diff.csv` |
| 4 | markdown | заголовок следующего блока |
| 5 | код, **production** | `build_elo_diff_table` — расчёт `elo_norm` → `elo_norm.csv` |

**Ручные константы (меняются перед каждым запуском):**
```python
ELO_CALIB = "t5_elo_calib"   # какую колонку players использовать как стартовый elo
TOURNAMENT = "5t"            # какой турнир из t_results обрабатывать
```

**Ячейка 3 — расчёт `elo_diff` по картам (source: notebook, подтверждена):**

1. Берётся `elo_calib` игрока как стартовый `elo` для турнира.
2. Для каждого коэффициента `koef` из `[0.2, 0.15, 0.1]` **по порядку** и для каждой карты
   турнира (`mapId` от 1 до максимума):
   - `combo = 3*Σkills + Σassists + 5*Σmvps + 0.2*Σadr` (сумма по всем игрокам на этой карте);
   - `elo_map[игрок] = round( (3*kills + assists + 5*mvps + 0.2*adr) / combo * Σelo )` —
     то есть суммарный `elo` всех участников карты распределяется пропорционально
     "перформанс-очкам" игрока на этой карте;
   - `elo_diff_map_koef = round((elo_map - elo) * koef)`;
   - `elo` игрока обновляется (`elo += elo_diff_map_koef`) и передаётся на следующую карту/пass.
3. Три прохода с koef `0.2 → 0.15 → 0.1` выполняются **последовательно по одним и тем же
   картам** (это релаксационная схема: карты пересчитываются 3 раза с уменьшающимся весом), а
   не "по одному проходу на карту".
4. Итоговый `elo_diff` по каждой карте — это сумма приростов со всех 3 проходов для этой
   карты (`groupby(id, mapId).sum()`), после `melt` в длинный формат.
5. Результат `elo_m3` по форме 1:1 совпадает с `cs_farpost_elo_changes.xlsx`
   (`id, mapId, elo_diff, tournament`).

**Ячейка 5 — расчёт `elo_norm` (source: notebook, подтверждена):**

Для каждого игрока и каждого турнира `t` по возрастанию: если это первый турнир игрока —
`elo_diff = t{t}_elo_start`; иначе `elo_diff = t{t}_elo_start - <elo, с которым игрок закончил
предыдущий турнир>`. Результат помечается `tournament = f"{t}a"`. Совпадает по форме с
`cs_farpost_elo_norm.xlsx`, **кроме строк `tournament == "7n"`**, которые этим кодом не
производятся (см. 3.2).

### 4.2 `cs_farpost_tournament_calib.ipynb` (10 ячеек)

| Ячейка | Тип | Назначение |
|---|---|---|
| 0 | код | импорты |
| 1 | markdown | описание источников |
| 2 | код | загрузка `players`, `t_results` |
| 3 | код, **production** | расчёт калибровочного `elo`/`elo_diff`/`elo_final` → `elo.csv` |
| 4–5 | markdown | заголовки |
| 6 | код, **исследовательский, не production** | выборка игроков одного калибровочного матча → `out.csv` |
| 7 | код, **исследовательский** | преобразование в список |
| 8 | код, **исследовательский** | брутфорс-балансировка 10 игроков на 2 команды по 5 (полный перебор `itertools.combinations`, минимизация разницы суммы `elo`) |
| 9 | код, **исследовательский** | проверка суммы `elo` по получившимся командам |

**Ручные константы:**
```python
ELO_START = "t7_elo_start"
TOURNAMENT = "7c"
```

**Ячейка 3** повторяет ту же карту-based итерацию, что и в `cs_farpost_tournament.ipynb`
(идентичная формула `elo_map`, идентичные коэффициенты `[0.2, 0.15, 0.1]`), но стартует от
`elo_start`, а не от `elo_calib`, и добавляет расчёт `elo_final`:

```python
def calculate_elo_final(row):
    t5_valid = notna(t5_elo) and t5_elo != 0
    t6_valid = notna(t6_elo) and t6_elo != 0
    if t5_valid and t6_valid:   return 0.3*t5_elo + 0.5*t6_elo + 0.2*elo
    elif t6_valid:              return 0.7*t6_elo + 0.3*elo
    elif t5_valid:               return 0.6*t5_elo + 0.4*elo
    else:                        return elo
elo_final = elo_final * (1000 * n_players) / elo_final.sum()   # нормировка: средний EloFinal == 1000
```

**Важно:** переменная `elo_final` вычисляется в памяти, но **не экспортируется ни в один
файл** (в `elo.csv` уходит только `id, mapId, elo_diff, tournament`; в `out.csv` — только
`fio, id, elo`, без `elo_final`). Значит, **исходники не содержат ни одной сохранённой
величины "EloFinal"** — ни в этих тетрадях, ни в пяти таблицах `data/raw/`. Формула для
`elo_final` **известна из кода**, но не подтверждено, что именно её показывает Power BI под
именем `EloFinal` на скриншотах (возможно, там показан просто `t{n}_elo` последнего турнира).

**Ячейки 6–9 — не относятся к расчёту Elo.** Это отдельный инструмент: для 10 игроков,
отмеченных `map{N} == 1` в `players.xlsx` (участники одного конкретного калибровочного
матча), полным перебором ищутся два состава по 5 человек с минимальной разницей суммарного
`elo`. Результат никуда не сохраняется и не попадает в исходные таблицы — это
"инструмент организатора" для формирования составов, не часть аналитического пайплайна.

## 6. Предварительная модель данных

Ниже — таблицы будущего аналитического слоя, обоснованные тем, что реально есть в файлах.
Это **предложение**, не итоговая схема — усложнять её сверх факта не стоит.

### `dim_tournament`
- **Grain:** один турнир/событие (регулярный `t`, калибровка `c`, нормализация `a`).
- **Ключ:** нормализованный код турнира, напр. `(number=5, kind="tournament"|"calib"|"norm")`.
- **Поля:** номер, тип, даты (min/max по `tournament_results.date`), место в общем списке.
- **Источники:** уникальные значения `tournament` из всех 4 таблиц, где она есть.
- **Проверки качества:** единое соответствие форматов `"5t"`/`"t5"`/`"5a"` → один код; явно
  задокументировать, что делать с `"7n"` (сейчас неизвестно).

### `dim_team`
- **Grain:** одна команда (по возможности — с учётом алиасов написания).
- **Ключ:** нормализованное имя команды (`strip + casefold` минимум; отдельная ручная таблица
  алиасов для случаев типа `RunChickenRun`/`RunChikenRun`).
- **Поля:** каноническое имя, список алиасов, департамент-принадлежность (если нужно).
- **Источники:** `team` из `tournament_results.xlsx`, `team` из `tournament_score.xlsx`,
  `t{n}_team` из `players.xlsx`.
- **Проверки качества:** явный alias-мэппинг перед джойном (см. раздел 3.6); без него часть
  команд из `tournament_score` не свяжется со статистикой на картах.

### `dim_player`
- **Grain:** один игрок.
- **Ключ:** `id` (slug), с `player_id`/`steam_name` как дополнительными идентификаторами.
- **Поля:** `steam_name`, `fio`* , `city`*, `department`*, `discord_name`*, `faceit_name`*,
  `faceit_link`*, `another_names` (поля, отмеченные `*`, — PII, для публичного дашборда
  нужно решение об исключении/анонимизации — см. блокеры).
- **Источники:** `cs_farpost_players.xlsx`.
- **Проверки качества:** 2 игрока (идентификаторы анонимизированы в этом документе) есть в справочнике, но не встречаются ни
  в `tournament_results`, ни в `elo_changes` — уточнить, активны ли они.

### `dim_map`
- **Grain:** одна карта CS2 (по названию `de_*`).
- **Ключ:** `map` (строка).
- **Поля:** название.
- **Источники:** `tournament_results.map` (8 значений). **Важно:** не путать с `mapId`
  (порядковый номер карты в турнире) и с `map1..map13` из `players.xlsx` (флаги калибровочных
  матчей) — это три разные сущности с похожими именами.

### `fact_player_tournament_map`
- **Grain:** игрок × турнир × номер карты (`mapId`) — одна сыгранная карта.
- **Ключ:** `(tournament, mapId, id)` — подтверждено уникальным на реальных данных.
- **Поля:** `matchId, map, date, rounds, result*, w/l, team, kills, deaths, assists, mvps,
  adr, headshots, headshots_percent, triple_kills, quadro_kills, penta_kills`, плюс
  `elo_diff` (джойн из `cs_farpost_elo_changes.xlsx` по `id, mapId, tournament`).
- **Источники:** `tournament_results.xlsx` + `elo_changes.xlsx`.
- **Проверки качества:** колонка `result*` смешивает даты и счёт — нужно решение, что с ней
  делать (см. раздел 7); `headshots`/`triple_kills`/… заполнены лишь в 13% строк.

### `fact_team_tournament_map` / `mart_team_map`
- **Grain:** команда × турнир × карта (агрегат `fact_player_tournament_map` по `team`).
- **Ключ:** `(tournament, mapId, team)`.
- **Поля:** суммарный/средний `elo_diff`, счёт, `w/l`, количество игроков в строке.
- **Источники:** агрегация `fact_player_tournament_map`.
- **Проверки качества:** зависит от alias-мэппинга команд (см. `dim_team`); нужно решить, что
  считать "count" в матрице team×map — количество карт, количество турниров, или сумму
  `elo_diff` (в задаче упомянуты все три варианта одновременно).

### `mart_player_summary`
- **Grain:** игрок (опционально — игрок × турнир, если фильтр по турниру должен резать summary).
- **Поля-кандидаты (см. точный статус в `metric_catalog.md`):** `steam_name`, `team` (текущая/
  за выбранный турнир), количество турниров, `kills/assists/deaths/adr` (сумма или среднее —
  не подтверждено), `KD`, `KR`, `avgKills2`, `elo_calib`, `EloFinal`, `elo_diff`, `elo_diff%`.
- **Источники:** `players.xlsx` + агрегаты `fact_player_tournament_map`.
- **Проверки качества:** для `KD`, `KR`, `avgKills2`, `EloFinal`, `elo_diff%` формула
  **не подтверждена** — эти поля нельзя посчитать без риска придумать её самостоятельно.

### `mart_team_summary`
- **Grain:** команда (опционально × турнир).
- **Поля-кандидаты:** `elo_calib`, `EloFinal`, `elo_diff`, `elo_diff%`, место на турнире
  (`tournament_score.place`).
- **Источники:** агрегация `mart_player_summary` по составу команды + `tournament_score.xlsx`.
- **Проверки качества:** состав команды у игрока меняется по турнирам — агрегат "команда" без
  указания турнира неоднозначен.

### `mart_rating_history`
- **Grain:** игрок × турнир (последовательность `elo_start → elo_calib → elo`).
- **Поля:** три точки Elo на турнир + `elo_diff` по картам этого турнира (для waterfall).
- **Источники:** `players.xlsx` (широкий формат `t{n}_elo_*`) развёрнутый в длинный формат +
  `elo_changes.xlsx` для детализации по картам внутри турнира.

`dim_tournament`, `dim_team`, `dim_player`, `dim_map`, `fact_player_tournament_map` можно
строить уже сейчас без гипотез. Марты (`mart_*`) частично зависят от метрик со статусом
"формула отсутствует" (раздел 7) — их структуру можно зафиксировать, но заполнить только
подтверждёнными полями до получения ответов от владельца отчёта.

## 7. Неизвестная Power BI-логика

Список показателей/преобразований, видимых на скриншотах, которые **отсутствуют** и в
notebook-коде, и как готовая колонка в `data/raw/`. Для каждого — что теоретически можно
посчитать, что нужно выгрузить из Power BI, и риск самостоятельного восстановления.

| Показатель | Что отсутствует | Как теоретически считается | Что нужно выгрузить из Power BI | Восстановимо однозначно? | Риск ошибки |
|---|---|---|---|---|---|
| `KD` | нет ни колонки, ни формулы | `Σkills / Σdeaths` или `AVERAGE(kills/deaths по карте)` — эти два варианта дают разные числа при разном числе карт у игроков | текст DAX-меры `KD` (или её описание) | Нет — стандартная метрика, но способ агрегации (сумма/сумма vs среднее отношений) не определён | Средний |
| `KR` | нет ни колонки, ни формулы | `Σkills / Σrounds` (рекомендуемый в CS способ) или `AVERAGE(kills/rounds)` | текст DAX-меры `KR` | Нет, по той же причине, что `KD` | Средний |
| `avgKills2` | нет ни колонки, ни объяснения, что означает "2" | неизвестно (могло быть "среднее за последние 2 турнира", "второй вариант формулы среднего", степень) | точное определение меры в Power BI (имя предполагает версионность, не квадрат — но это не факт) | **Нет** | Высокий — название неоднозначно, легко придумать неверную формулу |
| `elo_diff%` | нет колонки; `elo_diff` есть, но абсолютный | вероятно `elo_diff / elo_calib * 100` или `elo_diff / EloFinal * 100` | формула меры `elo_diff%` | Нет — знаменатель не определён | Средний-высокий |
| `EloFinal` | колонки с этим именем нет ни в одной таблице; в notebook есть похожая по названию переменная `elo_final`, но она не сохраняется | либо `t{n}_elo` последнего турнира игрока, либо notebook-переменная `elo_final` (взвешенная 0.3/0.5/0.2 комбинация t5/t6/текущего elo, ренормированная на среднее 1000) | какая колонка/мера в Power BI реально называется `EloFinal`, и её точная формула | Нет — два кандидата дают разные числа | Высокий |
| Рейтинг игрока (ranking) | нет измерения `RANKX` или готовой колонки места | `RANKX` по `EloFinal`/`elo_calib`/сумме `kills` — неизвестно, по какому полю | формула меры рейтинга | Нет | Средний |
| Рейтинг команды | нет измерения | агрегат Elo состава команды (сумма/среднее) либо `tournament_score.place` (это разные понятия — "силовой рейтинг" vs "итоговое место") | какая из двух трактовок используется на странице команды | Нет | Средний |
| Сравнение `elo_calib` vs `EloFinal` по командам | зависит от неизвестного способа агрегации Elo по составу команды и от неизвестной формулы `EloFinal` | среднее/сумма по игрокам команды на конкретном турнире | способ агрегации по команде + формула `EloFinal` | Нет | Средний-высокий |
| ADR/KD/KR как "профиль игрока" (усреднённые по турнирам/картам) | `adr` — сырая колонка на уровне карты; способ агрегации до игрока/турнира не описан | `AVERAGE` или `AVERAGEX` по картам | формула меры | Частично — само поле есть, неизвестна агрегация | Низкий-средний |
| Обработка колонки `result` (дата vs счёт) | смешанный формат, не объяснён нигде | нельзя восстановить бизнес-правило "когда дата, когда счёт" без первоисточника | исходная Google-таблица / описание процесса выгрузки | Нет | Высокий, если пытаться угадать правило |

**Принцип:** ни одна из этих метрик не будет реализована по угадыванию — на предыдущем шаге
проекта они помечаются как "формула отсутствует" в `docs/metric_catalog.md`, и в статике
дашборда (следующий этап) будут либо скрыты, либо явно помечены как "предположительно, требует
подтверждения", если пользователь решит их всё-таки показать с оговоркой.
